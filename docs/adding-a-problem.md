# Adding a problem

A *problem* is one small function you implement in a stub file, graded by a
hidden test. Problems are grouped under a two-digit **parent** (e.g. `04`) and
split into lettered **children** (`04a`, `04b`, …) — each child is one function
with its own test. Parents map to curriculum **tiers** by their integer range
(`curriculum.TIERS`).

The fastest path is the scaffolding tool, which writes the mechanical files for
you so you only think about the math. The manual steps are documented after, so
you know exactly what the tool does and how the pieces connect.

## The fluid way: `new_problem.py`

```bash
python new_problem.py 78a clip_to_unit --sig "(x, lo, hi)" --desc "clamp x into [lo, hi]"
```

This creates three files (and refuses to overwrite any that exist):

- `problems/p78a_clip_to_unit.py` — the stub you (or the learner) fill in, with
  `raise NotImplementedError` and the standard `__main__` runner block
- `.stubs/p78a_clip_to_unit.py` — a pristine copy so `reset.py` can restore it
- `tests/_src/test_p78a_clip_to_unit.py` — a test skeleton with the `step()`
  helper, the right import, and a `TODO` assertion

It also tells you which tier the parent falls in (and warns if none does). Then
finish three things and you're done:

1. **Write the test** in `tests/_src/test_p78a_clip_to_unit.py` — replace the
   `TODO` with real inputs and assertions (see *Writing the test* below).
2. **Add the reference** to `solutions.py` (see *The reference* below).
3. **Compile and verify:**
   ```bash
   python rebuild.py            # tests/_src/*.py -> tests/_compiled/*.pyc
   python verify_problems.py    # the reference must pass its own test
   ```

Once the test is compiled, the problem appears automatically in `check.py`,
`run_all.py`, the status dashboard, and `--next` — `curriculum.all_problem_ids()`
scans `problems/` and keeps any id with a test (`curriculum.has_test`).

## How the pieces connect

```
problems/p78a_clip_to_unit.py      # the editable stub (defines clip_to_unit)
.stubs/p78a_clip_to_unit.py        # pristine snapshot for reset.py
tests/_src/test_p78a_clip_to_unit.py    # readable test: test_p78a_clip_to_unit()
tests/_compiled/test_p78a_clip_to_unit.pyc   # generated by rebuild.py; what runner loads
solutions.py                       # PARENT_SOLUTIONS["78"] holds the reference
curriculum.py                      # TIERS maps parent 78 -> a tier
```

The grader (`runner.run_test_for`, called from the stub's `__main__`) loads the
compiled test, which does `from p78a_clip_to_unit import *` — picking up your
function — and runs `test_p78a_clip_to_unit()`. The **id, slug, and function
name must match** across the stub, the test filename + function, and the import.
The scaffolding tool keeps them in sync; if you go manual, mind that.

## Writing the test

Tests use a `step()` context manager (already in the skeleton) so a failed
assertion reports which sub-check broke. Keep it small and exact:

```python
def test_p78a_clip_to_unit():
    x = torch.tensor([-2.0, 0.5, 3.0])
    with step("clamps below lo and above hi"):
        assert torch.equal(clip_to_unit(x, 0.0, 1.0), torch.tensor([0.0, 0.5, 1.0]))
```

For float math use `torch.allclose` (not `equal`). For backward/gradient
problems, do a finite-difference check. Each `with step("..."):` block is one
labelled sub-check; use several when a function has distinct behaviours.

## The reference

`solutions.py` is a dict `PARENT_SOLUTIONS` keyed by the **two-digit parent**.
Each value is a source string containing the reference for *every* child of that
parent (plus any shared helpers). `get_solution("78a")` parses the child stub to
see which symbols it defines and slices just those out, so one parent entry
serves all its children — and `verify_problems.py` writes the whole parent source
behind the test, so shared helpers resolve.

- **New parent:** add a `"78": '''import torch\n\ndef clip_to_unit(x, lo, hi):\n    return x.clamp(lo, hi)\n'''` entry (under the matching tier banner).
- **Existing parent:** append your function to that parent's existing string.

Write the real implementation here — this is what `--solution` reveals and what
CI checks the test against.

## Tier placement

`curriculum.TIERS` is a list of `(name, first_parent, last_parent)`. The parent
must fall inside one range. If you're adding a parent number outside every range,
extend or add a tier tuple — otherwise the problem won't show in the dashboard
(`new_problem.py` warns you when this happens).

## Optional polish

All keyed by the **two-digit parent** (children inherit):

- `concepts.py` — `CONCEPTS["78"]`: a short blurb printed on PASS.
- `hints.py` — `HINTS["78"]`: a list of graduated hints for `check.py --hint`.
- `solutions.py` — `BENCHMARKS["78a"]`: `{"fn", "setup", "n_runs"}` to enable
  `check.py --time` (your impl vs the reference).
